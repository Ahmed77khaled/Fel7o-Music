# بروتوكول التعاون بين الوكلاء — Fel7o Downloader

> وثيقة مرجعية لعمل وكيلين (وأي إنسان) على نفس المستودع في نفس الوقت دون تعارض.
> **Manus** يعمل من بيئة سحابية معزولة، و**Google Antigravity** يعمل على جهاز المطوّر المحلي (ويندوز).

---

## 1. لماذا هذا التعاون؟

كلا الوكيلين قادر على كتابة الكود، لكن البيئتين مختلفتان جوهرياً — وهذا هو مصدر القوة، لا مشكلة يجب حلّها:

| القدرة | Antigravity (على الجهاز) | Manus (بيئة سحابية) |
|---|---|---|
| تشغيل تطبيق Electron حقيقي على ويندوز | ✅ | ❌ (لا واجهة رسومية بويندوز) |
| تجربة التنزيل الفعلي من يوتيوب | ✅ | ⚠️ جزئياً (yt-dlp متاح، لكن لا واجهة) |
| تصحيح تفاعلي بـ breakpoints ونافذة DevTools | ✅ | ❌ |
| رؤية الأثر البصري (CSS/تخطيط) | ✅ مباشرة | ⚠️ عبر لقطات |
| تحليل عشرات الملفات وربط الأنماط | ⚠️ محدود بسياق الجلسة | ✅ |
| أبحاث تقنية على الويب | ⚠️ | ✅ |
| تشغيل مهام طويلة (بناء، اختبارات، سكربتات) | ⚠️ يشغل الجهاز | ✅ معزول |
| إدارة GitHub (PRs, Issues, Releases, Actions) | ⚠️ يحتاج إعداد MCP | ✅ جاهز |
| التوثيق الطويل والتحرير المنظّم | ⚠️ | ✅ |

**الخلاصة:** Antigravity هو "اليد التي تلمس التطبيق الحقيقي"، وManus هو "العقل الذي يراجع ويخطط ويوثّق ويدير المستودع".

## 2. جسر التعاون: Git

الجسر الوحيد المطلوب فعلياً هو **المستودع نفسه** على GitHub: `Ahmed77khaled/Fel7o-Music-`.

```
┌────────────────────┐         ┌──────────────────┐
│  جهاز المطوّر      │         │  GitHub          │         ┌──────────────────┐
│  Antigravity IDE   │ ──push─▶│  Ahmed77khaled/  │◀─push── │  Manus (سحابة)   │
│  (ويندوز)          │◀─pull── │  Fel7o-Music-    │ ──pull─▶ │  بيئة معزولة     │
└────────────────────┘         └──────────────────┘         └──────────────────┘
          ▲                             ▲
          └────────── PR / مراجعة ──────┘
```

**لا حاجة لأي إعداد إضافي** غير أن يكون المستودع مستنسخاً محلياً لدى الطرفين مع صلاحية دفع. إعداد MCP اختياري ولاحق (القسم 6).

## 3. الأدوار المحدّدة

### Antigravity — يتولّى:
- تعديلات الواجهة: `src/index.html`, `src/renderer.js`, `src/styles.css`.
- تشغيل التطبيق فعلياً واختبار التدفقات: بدء تنزيل، إيقاف، استكمال، إلغاء، مدير قوائم التشغيل، السجل، الإعدادات.
- تشخيص الأخطاء التي لا تظهر إلا وقت التشغيل على ويندوز.
- اقتراح تحسينات تجربة المستخدم بناءً على الاستخدام الفعلي.
- توثيق أي خطأ مُشاهَد بأدلة: نص الخطأ + خطوات إعادة الإنتاج + لقطة.

### Manus — يتولّى:
- تعديلات `main.js` و`preload.js` والمنطق متعدد الملفات.
- مراجعة كل PR قبل الدمج (فحص الأمان، القواعد، التوافق مع عقود IPC).
- التدقيق الأمني: `webPreferences`, مدخلات yt-dlp, مسارات الملفات, حقن الأوامر.
- الأبحاث التقنية: تغييرات يوتيوب، إصدارات yt-dlp، بدائل المكتبات.
- CI/CD: GitHub Actions للبناء والتحقق من الإصدارات.
- تحديث `README.md` و`CHANGELOG.md` ووثائق `docs/`.
- إدارة الإصدارات ووسوم Git وإصدارات GitHub Releases.

### المطوّر (أنت) — يتولّى:
- القرار النهائي: أي ميزة تُبنى، وأي PR يُدمج.
- الموافقة على أي حزمة npm جديدة أو تغيير في رقم الإصدار.
- تشغيل البناء النهائي وتجربة الـ installer الناتج.

## 4. دورة العمل (Workflow)

```
  ① اختيار مهمة               ② فرع جديد              ③ تنفيذ
  docs/TASKS.md     ──▶      git checkout -b      ──▶   كود + اختبار
  (حدّد حالتها 🟡)             <agent>/T-0xx-slug        (تعريف منتهٍ ✓)

  ⑥ دمج في main                ⑤ مراجعة PR            ④ دفع + PR
  (المطوّر / الوكيل المراجع) ◀──  (الوكيل الآخر)   ◀──  git push + gh pr create
                                        │
                                        └──▶ تعليقات → إصلاح على نفس الفرع → إعادة مراجعة
```

### خطوات ملزمة

1. **اسحب آخر `main` قبل البدء:**
   ```bash
   git checkout main && git pull
   git checkout -b <agent>/<task-id>-<short-slug>
   ```
2. **نفّذ المهمة** وفق قواعد `AGENTS.md` القسم 4.
3. **حدّث السجلات قبل الدفع:**
   - `docs/TASKS.md`: الحالة → `🔵 بانتظار مراجعة`
   - `docs/HANDOFF.md`: أضف سطراً جديداً
   - `CHANGELOG.md`: إن كان التغيير ظاهراً للمستخدم
4. **ادفع وافتح PR:**
   ```bash
   git add -A
   git commit -m "<type>: <وصف موجز>" -m "Agent: <antigravity|manus>"
   git push -u origin <branch>
   gh pr create --fill --label collaboration
   ```
5. **راجع أو اطلب مراجعة.** لا يُدمج أي PR بلا مراجعة من الوكيل الآخر أو من المطوّر.

### اسمح بالتعارض قبل حدوثه
- **ملفات عالية التعارض:** `src/styles.css`, `src/renderer.js`, `main.js`.
- **قاعدة:** لا يعمل وكيلان على نفس الملف في نفس الوقت. تعيين الملفات يتم في `docs/TASKS.md` عمود "الملفات".
- عند حدوث تعارض: أعد التمركز على `main` (`git rebase main`) وحلّ التعارض يدوياً — **لا تستخدم `-X ours/theirs` أبداً**.

## 5. تنسيق رسائل Commit

```
<type>: <وصف موجز بالعربية أو الإنجليزية>

<تفاصيل اختيارية — لماذا وليس ماذا>

Task: T-0xx
Agent: <antigravity|manus>
```

`type` من المجموعة: `feat`, `fix`, `refactor`, `style`, `docs`, `chore`, `perf`, `security`, `ci`.

**مثال:**
```
fix: إصلاح استماع stderr عند استكمال تنزيل متوقف

كانت رسالة الخطأ تظهر عامة بدل السبب الحقيقي.
تم توحيد المعالجة في attachProcessHandlers().

Task: T-007
Agent: manus
```

## 6. إعداد MCP (اختياري — مرحلة لاحقة)

Antigravity يدعم خوادم MCP عبر `mcp_config.json`، وهذا يسمح له بإدارة GitHub مباشرة (PRs, Issues, Actions, Releases) بدل الطرفية.

- **الحد الأدنى المطلوب للتعاون: لا شيء.** Git وحده كافٍ.
- **الفائدة من MCP:** قدرة Antigravity على فتح/مراجعة/دمج PRs وتتبع الـ Issues دون مغادرة الـ IDE.
- **الشرط:** رمز وصول GitHub (PAT) بصلاحيات `repo` و`workflow`.

> **ملاحظة معمارية:** لا يمكن حالياً لـ Antigravity استدعاء Manus بشكل مباشر كمزوّد MCP، لأن بيئة Manus السحابية مؤقتة ولا تملك عنواناً دائماً. تحقيق رابط مباشر بين الوكيلين يتطلب بيئة دائمة (Persistent VM) تُشغّل خادم MCP مستقر — وهذا ممكن، لكنه خارج نطاق الإعداد الأولي.

---

## 7. عند حدوث خلاف تقني

1. **أوقفه فوراً**: علّق على الـ PR وسجّل الحالة في `docs/HANDOFF.md`.
2. **اعرض الطرفين**: ما تدعمه الأدلة (منطق الكود، الأداء، القيود التقنية).
3. **رجّح للمالك**: إذا تعذّر الاتفاق، القرار للمطوّر.
4. **سجّل النتيجة**: حتى القرارات المرفوضة تُسجَّل كي لا تُعاد مناقشتها.
